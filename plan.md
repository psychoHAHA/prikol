# План развития Draft Lab

## Цель

Сделать понятного помощника по драфту Dota 2: пользователь выбирает позицию, союзников и противников, а сервис показывает статистические контрпики, предметы и объяснения. Статистика STRATZ должна сопровождаться понятным размером выборки и ограничениями метода.

## Что уже сделано

- Проведён аудит проекта и текущей архитектуры.
- Frontend переведён на React + TypeScript.
- Backend переведён на TypeScript и разделён на маршруты, STRATZ-клиент, кэш, rate limit и сервисы данных.
- Добавлены доменные типы и API DTO.
- Реализованы загрузка героев и позиций, поиск контрпиков, предметы и guide.
- Добавлены обработка ошибок, отмена запросов, кэширование и ограничение частоты запросов.
- Добавлены unit-тесты frontend, API-клиента и серверной логики.
- Настроена общая проверка `npm run check`.
- Главная страница разделена на `pages`, `widgets` и `features`: `Header`, `Intro`, `DraftSetup`, `TeamPicker`, `RecommendationPanel`, `RecommendationCard`, `ItemBuild`, `Footer`.
- Последний frontend-коммит: `refactor(frontend): split draft page into widgets and features`.

## Текущий этап: удобство интерфейса

Статус: в работе.

### Утверждённое визуальное направление

**Draft Lab — спокойная тёмная аналитическая панель для драфта.**

- Графитовый фон и панели без декоративного шума.
- Лаймовый цвет используется для главного действия, фокуса и положительных акцентов.
- Терракотовый цвет используется только для противников и отрицательных matchup-сигналов.
- Небольшие скругления 8px, тонкие границы, заметные состояния hover/focus.
- Один главный CTA: `Найти контрпики`.
- Результаты читаются сверху вниз: герой, итоговая статистика, причины, предметы и ссылки на исходные матчи.
- Тексты STRATZ, экспертные советы и ограничения выборки визуально разделены.
- На мобильном интерфейс становится последовательным: ввод драфта, затем результаты; кнопка анализа остаётся доступной после заполнения формы.

### Дизайн-система

Зафиксировать в `src/app/styles.css` токены:

- цвета фона, панели, границ, текста, muted-текста, accent, ally и enemy;
- размеры контейнера, отступы, радиусы и высоту контролов;
- типографическую шкалу для заголовка, секции, текста и подписи;
- состояния `hover`, `focus-visible`, `disabled`, `loading`, `error` и `empty`.

### Порядок работ по UI

1. Проверить текущую страницу вручную на реальном API и зафиксировать проблемы.
2. Привести CSS к токенам и единым интерактивным состояниям.
3. Улучшить `TeamPicker`: видимые слоты, понятные лимиты, клавиатурная навигация, закрытие списка по Escape и доступный focus.
4. Обновить карточку рекомендации: крупный процент, число матчей, confidence или пометка о размере выборки, отдельный блок «Почему этот герой».
5. Переработать `ItemBuild`: этапы покупки, время, частота и ссылка на guide.
6. Добавить стабильные skeleton/loading-состояния без скачков layout.
7. Добавить понятные состояния ошибки API, пустого результата и недостаточной выборки с действием повторить запрос.
8. Проверить мобильные ширины 320px, 375px, 768px и desktop.
9. После каждого законченного шага запускать `npm run check` и делать ручной просмотр страницы.

## Ближайшая техническая задача

Перед визуальной полировкой проверить production-конфигурацию STRATZ:

1. Убедиться, что `STRATZ_TOKEN` задан в окружении Render.
2. Проверить, что токен не содержит кавычек и лишних пробелов.
3. Проверить логи сервера и определить, приходит ли 403 от STRATZ из-за токена, прав доступа или лимита API.
4. После исправления переменной выполнить redeploy и пройти сценарий вручную.

Ошибка `STRATZ ответил HTTP 403` относится к серверному доступу STRATZ и не исправляется перестановкой React-компонентов.

## Визуальная концепция: Draft Cockpit

Главный экран строится вокруг одного сценария: быстро описать драфт и понять, почему система предлагает героя.

- Вверху — компактная шапка с названием, патчем и статусом источника данных.
- Под шапкой — короткий заголовок и объяснение без большого декоративного hero-блока.
- Основная область — две панели на desktop: слева «Твой драфт», справа «Рекомендации».
- На мобильном панели идут последовательно: сначала ввод, затем результаты.
- Выбор позиции — отдельный заметный control с понятными русскими названиями.
- Союзники и противники показываются как слоты с аватаром, именем и удалением; цвета команд различаются умеренно.
- Результат начинается с крупного рейтинга и процента, затем показывает число матчей, confidence и причины выбора.
- Блок «Почему этот герой» разделяет статистические факторы STRATZ и экспертные правила.
- Предметы отображаются как последовательность этапов с таймингом, частотой и пояснением, а не длинным текстом.
- Предупреждения о маленькой выборке и ограничениях метода видны рядом с данными.
- Все интерактивные элементы имеют клавиатурный focus, disabled/loading/error-состояния и не меняют высоту экрана скачком.

Не добавляем декоративные игровые панели, постоянные графики и сложные анимации: они будут мешать главному действию — сравнению рекомендаций.

## Подготовка экспертных данных

Пользовательский файл с героями, контрпиками и предметами становится исходным материалом для базы знаний. Его не подключаем к UI напрямую.

Базовая форма записи согласована:

```json
{
  "hero": "Sniper",
  "summary": "...",
  "counters": [
    {
      "hero": "Spectre",
      "roles": ["carry"],
      "reason": "Dispersion отражает урон, а Shadow Step и Haunt позволяют быстро добраться до Снайпера."
    }
  ],
  "items": [
    {
      "item": "Blink Dagger",
      "reason": "Помогает инициаторам быстро сократить дистанцию."
    }
  ],
  "tips": ["Стараться атаковать Снайпера с нескольких направлений."]
}
```

После нормализации записи дополняются каноническими `heroId` и `itemId`,
патчем, источником, датой обновления и confidence. По этим ID frontend
строит портрет героя и иконку предмета, а URL изображений не дублируются в
каждом JSON-объекте.

Визуально экспертная информация показывается в карточке рекомендации блоками:
портрет и рейтинг героя, «Почему этот герой», ряд иконок предметов, советы и
ссылка на статистику STRATZ. На мобильном эти блоки идут вертикально.

Pipeline:

1. Принять исходный файл в согласованном формате: JSON, YAML или Markdown по шаблону. Для теста разобраны разделы Alchemist, Axe и Bristleback из `контрпики.txt`.
2. Зафиксировать схему записи: герой, позиция, противник или условие, предмет, объяснение, патч, источник, приоритет и confidence.
3. Написать отдельный скрипт нормализации, который приводит имена героев и предметов к каноническим ID из `/api/heroes` и STRATZ.
4. Добавить проверку схемы: обязательные поля, допустимые позиции, существующие ID, отсутствие дубликатов и корректные значения confidence.
5. Генерировать нормализованный файл `src/shared/data/knowledge.json` с версией схемы и датой обновления. Первый тестовый файл создан для трёх героев; канонические ID будут добавлены на следующем шаге нормализации.
6. Добавить тесты для нормализации и примеры ошибочных записей.
7. Использовать JSON в frontend для блока «Почему этот герой» и экспертных подсказок по предметам. Тестовое подключение выполнено в карточке рекомендации.
8. Показывать источник и дату проверки рядом с экспертным советом.

Статистическая рекомендация STRATZ остаётся отдельным фактором. Экспертное правило может объяснить выбор и предложить действие, но не должно скрывать размер статистической выборки.
## Следующий функциональный этап: база игровых знаний

Статус: после стабилизации визуала.

Добавить экспертные материалы по нескольким героям, начиная со Снайпера. Каждое правило хранить в структуре:

- герой;
- контрпик;
- позиция;
- предмет;
- игровое условие;
- объяснение;
- патч или дата проверки;
- источник;
- приоритет и уверенность.

Статистические данные STRATZ и экспертные объяснения отображаются раздельно, после чего объединяются в одну рекомендацию с понятными подписями.

## Дальнейшие этапы

### Данные и хранение

- PostgreSQL и Prisma.
- Таблицы героев, предметов, патчей, матчапов, покупок и экспертных правил.
- Фоновая загрузка и нормализация данных STRATZ.
- Источник, патч, период, размер выборки и дата обновления для статистики.

### Алгоритм

- Учитывать позицию противника и союзную синергию.
- Добавить patch-aware scoring, confidence score и минимальный размер выборки.
- Показывать вклад факторов в итоговый рейтинг.
- Для каждого изменения добавлять тесты и сравнение с текущей формулой.

### Backend и production

- Сохранить текущие API-контракты при переходе на постоянное хранилище.
- При необходимости перейти на NestJS после стабилизации текущего сервера.
- Добавить Redis, health checks, структурированные логи, CI, Docker, OpenAPI и integration tests.
- Проверить условия использования STRATZ и внешних источников экспертных данных.
